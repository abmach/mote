Elements and platform behavior

mote styles ordinary HTML before it reaches for classes. Start with the element that already carries the meaning.

Elements

Everything below is plain semantic HTML — no classes, no attributes beyond semantics. The gallery on the layout and components page renders the complete set.

Definition lists

Definition lists align terms and descriptions in two columns without classes. Both direct dt/dd children and valid grouping wrappers keep the same aligned rows:

<dl>
  <dt>Format</dt>
  <dd>CSS</dd>
  <dt>Dependencies</dt>
  <dd>None</dd>
</dl>

<!-- group each term with its description -->
<dl>
  <div>
    <dt>Format</dt>
    <dd>CSS</dd>
  </div>
  <div>
    <dt>Dependencies</dt>
    <dd>None</dd>
  </div>
</dl>

For mote's two-column layout, direct children alternate one term with one description. The grouping div is structural, not another visual row: use one term and one description per wrapper. Both structures then keep terms in one column and descriptions in the other.

In a narrow rail — the reference aside of the document shell is about 250px — the two columns get cramped; stack that one list with the recipe above.

Tables

Numeric figures align automatically — mote sets font-variant-numeric: tabular-nums on every td. Right-align a whole column with the opt-in .mote-num class on its cells; when you want the tabular figures without the alignment (day numbers, headline figures, meta lines), use .mote-tabular instead:

<th class="mote-num">Price</th>
<td class="mote-num">$24</td>

For sticky headers and scrollable data tables, wrap in the opt-in .mote-table-scroll — the header row sticks, wide tables scroll inside the wrapper, never the page. Cap the panel height with --mote-table-max (default 60vh); the sticky header engages once the wrapper actually scrolls. The page and the wrapper have distinct scroll regions: the page may scroll vertically, the wrapper owns horizontal overflow, and the wrapper also scrolls vertically when its content exceeds the cap. A tall table can therefore scroll inside the wrapper before the page reaches it. The content is not cropped; move the pointer or keyboard focus over the wrapper and use its scrollbar or arrow keys. On paper, the wrapper releases the screen height cap and clipping so the complete table is present in the output; a very wide table may still exceed narrow paper, and mote does not shrink an arbitrary matrix. Inside the wrapper, cell borders are drawn per side — Chromium paints collapsed borders at the flow position, not with the sticky cell:

<div class="mote-table-scroll">
  <table>…</table>
</div>

<!-- dense panels: cap the height -->
<div class="mote-table-scroll" style="--mote-table-max: 24rem">
  <table>…</table>
</div>

Narrow screens: scroll or transform

Choose the representation before the breakpoint. Keep a comparison or data matrix as one semantic table and let its wrapper own sideways scrolling. For independent records that people read one at a time, use semantic articles or definition lists instead — a card-per-record layout is usually easier to scan on a phone.

Do not render both a table and a card copy and hide one with CSS: duplicated content becomes ambiguous for assistive technology and search. The same records may appear in a second representation only when it presents genuinely distinct information or serves a different task; otherwise mark the current row inside the table with aria-current and use the row-tint recipe below. When the table is the only representation, give its scroll region an accessible name and keyboard focus:

<div class="mote-table-scroll" tabindex="0" role="region" aria-label="Product comparison">
  <table>…</table>
</div>

The wrapper keeps the page still while the table moves. On paper, mote's components file removes the wrapper's artificial clipping and height cap; the complete table is present, but a wide matrix may still exceed the paper width.

When one table must become readable records on a phone, transform that same table instead of adding a second, hidden card copy. Every data cell in the transformed branch must have a non-empty data-label. The attribute supplies the visible label when the table becomes records. A missing data-label produces a blank label beside the value; this applies to every transformed , not only the first column. Then change the table's visual layout below the chosen breakpoint. The markup remains one table rather than duplicated content. Current Chromium retains the table, row, header, and cell roles in this layout; because CSS display changes can affect semantics in other engines, verify the recipe with the browsers and assistive technology you support:

<table class="records">
  <caption>Autumn fixtures</caption>
  <thead>
    <tr><th>Date</th><th>Fixture</th><th>Ground</th></tr>
  </thead>
  <tbody>
    <tr>
      <td data-label="Date">12 Oct</td>
      <td class="mote-num" data-label="Score">24–18</td>
      <td data-label="Fixture">Riverside v Northfield</td>
      <td data-label="Ground">Meadow 2</td>
    </tr>
  </tbody>
</table>

Keep the semantic table as the only representation. If each record needs a different phone layout, prefer articles or definition lists instead of adding increasingly specific table transformations.

The 40rem breakpoint in this recipe is an example, not a mote default. Choose the threshold before copying the recipe: a wide desktop matrix may need to remain a table until a narrower width, while a record list can transform earlier. A custom breakpoint cannot be parameterized with a CSS variable inside @media. Copy the recipe and replace the threshold in both the transform query and the cap-release query, keeping them identical. The print-restoration rules remain unchanged regardless of the selected breakpoint.

Phone-record checklist

  • Choose the representation first. A retained comparison matrix remains valid; do not transform it merely because the page also contains record-style tables.
  • Apply the recipe to every table the author chooses to transform, and apply each recipe completely.
  • Give every transformed td a non-empty data-label.
  • Keep the complete print restoration: table display, header row, sticky cells, caption, and generated labels.
  • When a transformed table stays inside .mote-table-scroll, release its height cap in the same narrow query.
  • Verify the chosen narrow width has no page-level horizontal overflow, then inspect the generated PDF.

Several details of this recipe are load-bearing. The label column is one knob for the whole table — --records-label, 7rem by default — so every record's labels line up with each other; widen it once when a label is longer than the default. The label keeps text-align: start, so a right-aligned numeric column does not drag the label to the far edge away from its value; numeric values also start-align in the record branch, where a label/value grid replaces table-column alignment. The print guard restores the table, its header row and its caption: the phone layout hides the header, so a print rule that only reverted display would print a table with no columns. It also removes the generated labels and resets sticky header cells, so narrow-viewport print emulation and paged output restore the table completely.

The transform branch does not need .mote-table-scroll — records no longer scroll sideways. When one table serves both branches, keep the wrapper for the wide matrix and release its height cap in the narrow query, or the panel crops the records it now contains. Name the wrapper and release the cap by that name — no selector magic needed:

<div class="mote-table-scroll records-panel">
 <table class="records">…</table>
</div>

<style>
@media (width < 40rem) {
 .records-panel {
    --mote-table-max: none;
 }
}

Mark the current row with aria-current — the same vocabulary as nav pills. The tint reads over zebra (the regression fixture asserts it on both parities):

<tr aria-current="true">…</tr>

Status classes remain token carriers: a status on a table row sets the row's tokens but paints nothing by itself. The page owns the visual row policy. Choose a class for your markup — here, .status-row — and add it to the row with the status class:

<tr class="status-row mote-warning">
  <th scope="row">Order 1048</th>
  <td>Needs review</td>
</tr>

Copy this page rule to paint the row's direct cells with the status it declares:

tr.status-row:is(.mote-success, .mote-warning, .mote-error, .mote-info)
  > :is(td, th[scope="row"]) {
  background-color: var(--mote-status-soft);
}

The selector preserves semantic row headers and uses background-color, so a column's background-image layer — such as the weekend shading below — remains intact:

Only direct cells are painted. Badges and buttons remain gated and keep their own status instead of inheriting the row's tint.

Captions center by default; a quiet left-aligned caption is one page rule: caption { text-align: start }.

Forms

Labels, inputs, selects, checkboxes, radios and buttons inherit the cozy surface. Invalid fields show a brick border once the user interacts with them (:user-invalid).

Timing is the browser's: text and email fields can fail as soon as you leave them, while Chromium marks a required <select> invalid on a submit attempt rather than on blur.

Fields keep their intrinsic width — for stacked forms, add input, select, textarea { width: 100% } in your page styles; inline forms are equally valid, so mote does not decide for you.

Or use the opt-in .mote-stack class — a vertical rhythm for forms and lists: children space by --mote-stack-gap (default 1.25rem) with their block margins zeroed, fields stretch full width, checkboxes/radios stay at 1em. It stacks any content, not just forms. On a <fieldset> it flattens the native legend notch — the legend renders as the first line inside the box, which reads fine for most forms:

<form class="mote-stack">
  <p><label for="name">Name</label> <input id="name" type="text"></p>
</form>

File inputs get a minimal drop-zone treatment — a dashed border and the same density tokens as every other control, so their height matches sibling fields in a stack.

Programmatic validation: aria-invalid="true" gets the same brick border as :user-invalid, so server-side and failed-save states are styleable without waiting for user interaction. A canonical search form (sr-only label + inline row):

<form class="mote-row" role="search">
  <label class="mote-sr-only" for="q">Search</label>
  <input id="q" type="search" placeholder="Search…">
  <button type="submit">Go</button>
</form>

Buttons and statuses

All button styles — solid and ghost — are gated: the status class must sit on the button itself. A themed section — an error note, a toast, a page-level body class="mote-error" — never recolors the actions inside it. Statuses theme content; they never theme actions. The intent of an action is declared at the action site:

<button>Neutral action</button>
<button class="mote-error">Delete forever</button>
<button class="mote-ghost">Quiet action</button>
<button class="mote-ghost mote-success">Confirm quietly</button>

Ghost buttons follow the same law. Inside a themed section, a ghost stays accent-tinted; to make it match the section's status, put the status class on it explicitly — class="mote-ghost mote-error" for a quiet destructive, class="mote-ghost mote-success" for a quiet confirm. Ghosts work on buttons and anchors alike.

<button class="mote-ghost">Cancel</button>
<a class="mote-ghost" href="/docs">Read the docs</a>
<button class="mote-ghost mote-error">Delete draft</button>

Get started quietly

Solid button on an anchor — .mote-btn is the opt-in class for the full solid recipe on any element:

<a class="mote-btn" href="/signup">Get started</a>

Display text

Opt-in hero/error-code scale via .mote-display — the body heading scale is untouched. Widen per use with the --mote-display variable. Display text reads --mote-status so a themed page (e.g. body class="mote-error") tints the giant code:

Semantic feedback

[role="alert"] and [role="status"] are styled as semantic feedback. They read --mote-status when one is present; otherwise role="alert" falls back to the error color and role="status" falls back to the info color. A status class on the element or an ancestor sets their text color:

<p role="alert" class="mote-error">Invalid email</p>
<p role="status">Saved</p>

Meters keep their native zone coloring (green/yellow/red from low/high/optimum) in some engines; the status class tints the gauge wherever the engine honors it.

A native <progress> keeps its intrinsic width — set progress { width: 100% } in your page styles when you want a full-width bar.

Dialogs

Native <dialog> gets a soft surface, a dimmed blurred backdrop, and — with the components file — a gentle entrance animation. Opening a modal takes one line of JavaScript:

<dialog id="example">
  <h3>Modal title</h3>
  <p>Content…</p>
  <form method="dialog"><button>Close</button></form>
</dialog>

<script>
  document.querySelector('#open-btn').onclick = () =>
    document.querySelector('#example').showModal();
</script>

A cozy modal

Backdrop dim, gentle fade, native Esc-to-close. The form method="dialog" button closes it declaratively.

One dialog can serve many items: fill its fields from the trigger before opening it, then close it with form method="dialog". The wiring is the page's own code — mote ships none.

A submit button inside form method="dialog" follows native form validation. If the form contains a required control, a cancel button would be blocked by that validation instead of closing the dialog. Add formnovalidate to the cancel button so it always closes the dialog:

<form method="dialog">
  <label>Delivery method
    <select name="delivery" required>
      <option value="" selected>Choose a method</option>
      <option value="standard">Standard</option>
    </select>
  </label>
  <button value="cancel" formnovalidate>Cancel</button>
  <button value="confirm">Confirm</button>
</form>

This is native HTML behavior, not mote behavior. Keep validation on the confirming action; only the cancel button skips it.

<dialog id="lot-dialog">
  <form method="dialog">
    <h3>Place a bid</h3>
    <label>Amount <input type="number" name="amount" min="45" step="0.50"></label>
    <button>Confirm</button>
  </form>
</dialog>

<script>
  const dialog = document.querySelector('#lot-dialog');
  document.querySelectorAll('[data-bid-for]').forEach(button => {
    button.onclick = () => {
      dialog.querySelector('input[name="amount"]').min = button.dataset.min;
      dialog.showModal();
    };
  });
</script>

Details and accordions

Single <details> elements are soft cards. Give a group of siblings the same name and the browser turns them into an exclusive accordion — one open at a time, no JavaScript. Try it:

An exclusive group spans the whole document: two disclosures that share a name close each other even when they sit in different cards. Give unrelated panels distinct names.

<details name="faq">
  <summary>Does it need a build step?</summary>
  <p>No.</p>
</details>
<details name="faq">
  <summary>Does it need classes?</summary>
  <p>No.</p>
</details>
Does it need a build step?

No. It is a single CSS file.

Does it need classes?

Not for elements. The optional components file adds a handful where no semantic element exists.

Does it need JavaScript?

No. Tooltips, menus and accordions ride on native platform features.

In Chromium engines, opening and closing also animates smoothly — a details pseudo-element nicety provided by the components file. Everywhere else the toggle is instant.

Printing note: the browser enforces one open panel per exclusive group, so printing "everything open" needs a beforeprint listener that removes the name attribute (and restores it after). The print stylesheet already forces the light palette, so dark-mode users get paper colors, not ink floods.

Print helpers: .mote-no-print hides any element on paper; .mote-print-only shows only in print:

<header class="mote-no-print">…</header>
<p class="mote-print-only">Printed notice</p>

Summary markers read the status classes too — moss, honey, brick, dusty-blue or neutral markers, from one class on the details element:

<details class="mote-success">
  <summary>A summary with a moss-green marker</summary>
  <p>Content…</p>
</details>

Popovers: tooltips and menus

The native popover attribute gives you top-layer, light-dismiss, Esc-to-close surfaces — styled by mote, wired by the browser. A popovertarget button toggles one with zero JavaScript:

<button popovertarget="tip">What is a mote?</button>
<div popover class="mote-tooltip" id="tip">
  A speck of dust, especially one drifting in a sunbeam.
</div>

<button popovertarget="menu">Options</button>
<menu popover id="menu" role="menu">
  <li><button role="menuitem">Rename</button></li>
  <li><button role="menuitem">Duplicate</button></li>
  <li><button role="menuitem">Archive</button></li>
</menu>

A speck of dust, especially one drifting in a sunbeam.

    • By default, the browser opens popovers centered in the viewport. To place one next to its trigger instead, use CSS anchor positioning (Chrome 125+, Safari 26+): give the trigger an anchor-name and the popover a matching position-anchor — mote then positions it right below the trigger and flips it when it would overflow the viewport. Engines without support keep the centered fallback:

    <button popovertarget="menu" style="anchor-name: --menu-a">Options</button>
<menu popover id="menu" style="position-anchor: --menu-a" role="menu">
  <li><button role="menuitem">Rename</button></li>
</menu>

    The live examples above are anchored — in Chromium and Safari they open next to their buttons; in Firefox they open centered.

    Anchored popovers sit below their trigger, centered on it, and flip above it when they would overflow the viewport. mote separates them with a 0.45rem margin. Chromium adds its own offset to the popover's placement, so the visible separation there is a little larger than the margin. Override it in page CSS when a surface needs more breathing room:

    [popover].mote-tooltip {
  margin: 0.75rem;
}

    The margin belongs to the anchored placement, so it travels with the popover when the browser flips it.
