mote.css

The smallest thing that can carry style — a tiny, semantic, class-optional CSS layer for plain HTML. Zero dependencies, zero build step, zero JavaScript.

Principles

  • Semantic HTML is the API. Elements are styled by what they are; classes exist only where the platform has no semantic carrier.
  • The platform before the library. Dialogs, popovers, accordions and validation use native features, quietly styled — mote never ships JavaScript to do what the browser already does.
  • Tokens all the way down. Every color, radius, shadow and status is a variable; derived tones are computed, never hand-tuned twice.
  • Weightless by default. One file for elements, an opt-in second file for components — zero bytes of library JavaScript.
  • Unobtrusive. Warm, soft, accessible; styling that never shouts.

Get started

Drop one file in your page and write plain HTML. Everything is styled by element — no utility classes, no framework, no build.

<!DOCTYPE html>
<html lang="en">
  <head>
    <link rel="stylesheet" href="mote.css">
    <title>That's it.</title>
  </head>
  <body>
    <h1>Hello, cozy.</h1>
  </body>
</html>

Out of the box, mote falls back to your system fonts; two link tags give it the intended look — see Fonts.

Optional components — cards, badges, popovers, accordions, spinners — live in a second stylesheet. Include it only if you use them:

<link rel="stylesheet" href="mote.css">
<link rel="stylesheet" href="mote.components.css">

This page is a live demo: it is styled by exactly those two files.

Theming

Every color, radius, shadow and font flows from --mote-* custom properties. Override a few tokens and the whole library re-themes — derived tones (focus rings, hover deepening, tinted surfaces) are computed with color-mix(), so you never hand-tune a second palette.

The cascade has three layers, each computed from the last: the base palette feeds derived tones (soft tints, hover deepening, focus rings — re-derived automatically whenever a base token changes), and status classes add a third indirection on top. Inheriting content surfaces read the --mote-status tokens with an accent fallback, while gated actions and badges declare their own status. Override the chain anywhere; everything downstream follows.

Live proof — this card re-themes everything inside it with two inline tokens:

<div class="mote-card" style="--mote-accent: #4a7a5b; --mote-on-accent: #ffffff">
  <h3>Re-themed card</h3>
  <p>A <a href="#">link</a>, a <button type="button">button</button> and a
    <span class="mote-badge mote-success">badge</span> — all from
    two variables.</p>
</div>

Re-themed card

A link, a and a badge — all from two variables. The focus ring, hover states and soft tints re-derived automatically.

:root {
  --mote-accent: #4a7a5b;    /* your brand color */
  --mote-on-accent: #ffffff; /* readable text on accent fills */
  --mote-bg: #fffdf5;        /* your paper */
  --mote-radius: 6px;        /* your edges */
}

When replacing --mote-accent, replace --mote-on-accent too: mote cannot infer whether white or dark text has enough contrast on an arbitrary brand color. A separate dark-theme accent may need its own foreground token as well.

Brand themes

A brand needs more than one declaration. mote's own palette rules are more specific than a plain :root override, so a lone :root { --mote-accent: … } is superseded in automatic dark mode and on paper. Restate the brand in every state it can appear in — and always pair the accent with its foreground token:

:root {
  --mote-accent: #4a7a5b;      /* brand in light and automatic light mode */
  --mote-on-accent: #ffffff;
}

:root[data-theme="dark"] {
  --mote-accent: #8fc7a1;      /* brand in forced dark mode */
  --mote-on-accent: #10231a;
}

@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) {
    --mote-accent: #8fc7a1;    /* brand in automatic dark mode */
    --mote-on-accent: #10231a;
  }
}

@media print {
  :root,
  :root[data-theme="dark"],
  :root:not([data-theme="light"]) {
    --mote-accent: #4a7a5b;    /* brand on paper */
    --mote-on-accent: #ffffff;
  }
}

Those selectors match mote's own palette rules, so your values win by order — override only the tokens you need and every derived tone re-derives from the accent you set. The @media print block is the one most pages forget: mote prints on a light paper palette, so without it paper keeps mote's accent instead of yours.

Tables

Numeric figures align automatically — mote sets font-variant-numeric: tabular-nums on every td. Right-align a whole column with the opt-in .mote-num class on its cells; when you want the tabular figures without the alignment (day numbers, headline figures, meta lines), use .mote-tabular instead:

<th class="mote-num">Price</th>
<td class="mote-num">$24</td>

For sticky headers and scrollable data tables, wrap in the opt-in .mote-table-scroll — the header row sticks, wide tables scroll inside the wrapper, never the page. Cap the panel height with --mote-table-max (default 60vh); the sticky header engages once the wrapper actually scrolls. On paper, the wrapper releases the screen height cap and clipping so the complete table is present in the output; a very wide table may still exceed narrow paper, and mote does not shrink an arbitrary matrix. Inside the wrapper, cell borders are drawn per side — Chromium paints collapsed borders at the flow position, not with the sticky cell:

<div class="mote-table-scroll">
  <table>…</table>
</div>

<!-- dense panels: cap the height -->
<div class="mote-table-scroll" style="--mote-table-max: 24rem">
  <table>…</table>
</div>

Narrow screens: scroll or transform

Choose the representation before the breakpoint. Keep a comparison or data matrix as one semantic table and let its wrapper own sideways scrolling. For independent records that people read one at a time, use semantic articles or definition lists instead — a card-per-record layout is usually easier to scan on a phone.

Do not render both a table and a card copy and hide one with CSS: duplicated content becomes ambiguous for assistive technology and search. The same records may appear in a second representation only when it presents genuinely distinct information or serves a different task; otherwise mark the current row inside the table with aria-current and use the row-tint recipe below. When the table is the only representation, give its scroll region an accessible name and keyboard focus:

<div class="mote-table-scroll" tabindex="0" role="region" aria-label="Product comparison">
  <table>…</table>
</div>

The wrapper keeps the page still while the table moves. On paper, mote's components file removes the wrapper's artificial clipping and height cap; the complete table is present, but a wide matrix may still exceed the paper width.

When one table must become readable records on a phone, transform that same table instead of adding a second, hidden card copy. Put a short label on each data cell, then change the table's visual layout below the chosen breakpoint. The markup remains one table rather than duplicated content. Current Chromium retains the table, row, header, and cell roles in this layout; because CSS display changes can affect semantics in other engines, verify the recipe with the browsers and assistive technology you support:

Four details of this recipe are load-bearing. The label column is one knob for the whole table — --records-label, 7rem by default — so every record's labels line up with each other; widen it once when a label is longer than the default. The label keeps text-align: start, so a right-aligned numeric column does not drag the label to the far edge away from its value; numeric values also start-align in the record branch, where a label/value grid replaces table-column alignment. The print guard restores the table, its header row and its caption: the phone layout hides the header, so a print rule that only reverted display would print a table with no columns. It also removes the generated labels and resets sticky header cells, so narrow-viewport print emulation and paged output restore the table completely.

The transform branch does not need .mote-table-scroll — records no longer scroll sideways. Forms

Labels, inputs, selects, checkboxes, radios and buttons inherit the cozy surface. Invalid fields show a brick border once the user interacts with them (:user-invalid).

Timing is the browser's: text and email fields can fail as soon as you leave them, while Chromium marks a required <select> invalid on a submit attempt rather than on blur.

Fields keep their intrinsic width — for stacked forms, add input, select, textarea { width: 100% } in your page styles; inline forms are equally valid, so mote does not decide for you.

Or use the opt-in .mote-stack class — a vertical rhythm for forms and lists: children space by --mote-stack-gap (default 1.25rem) with their block margins zeroed, fields stretch full width, checkboxes/radios stay at 1em. It stacks any content, not just forms. On a <fieldset> it flattens the native legend notch — the legend renders as the first line inside the box, which reads fine for most forms:

<form class="mote-stack">
  <p><label for="name">Name</label> <input id="name" type="text"></p>
</form>

File inputs get a minimal drop-zone treatment — a dashed border and the same density tokens as every other control, so their height matches sibling fields in a stack.

Programmatic validation: aria-invalid="true" gets the same brick border as :user-invalid, so server-side and failed-save states are styleable without waiting for user interaction. A canonical search form (sr-only label + inline row):

<form class="mote-row" role="search">
  <label class="mote-sr-only" for="q">Search</label>
  <input id="q" type="search" placeholder="Search…">
  <button type="submit">Go</button>
</form>

Buttons and statuses

All button styles — solid and ghost — are gated: the status class must sit on the button itself. A themed section — an error note, a toast, a page-level body class="mote-error" — never recolors the actions inside it. Statuses theme content; they never theme actions. The intent of an action is declared at the action site:

<button>Neutral action</button>
<button class="mote-error">Delete forever</button>
<button class="mote-ghost">Quiet action</button>
<button class="mote-ghost mote-success">Confirm quietly</button>

Ghost buttons follow the same law. Inside a themed section, a ghost stays accent-tinted; to make it match the section's status, put the status class on it explicitly — class="mote-ghost mote-error" for a quiet destructive, class="mote-ghost mote-success" for a quiet confirm. Ghosts work on buttons and anchors alike.

<button class="mote-ghost">Cancel</button>
<a class="mote-ghost" href="/docs">Read the docs</a>
<button class="mote-ghost mote-error">Delete draft</button>

Details and accordions

Single <details> elements are soft cards. Give a group of siblings the same name and the browser turns them into an exclusive accordion — one open at a time, no JavaScript. Try it:

An exclusive group spans the whole document: two disclosures that share a name close each other even when they sit in different cards. Give unrelated panels distinct names.

<details name="faq">

  <p>No.</p>
</details>
<details name="faq">
  <summary>Does it need classes?</summary>

Does it need a build step?

No. It is a single CSS file.

Does it need classes?

Not for elements. The optional components file adds a handful where no semantic element exists.

Does it need JavaScript?

No. Tooltips, menus and accordions ride on native platform features.

In Chromium engines, opening and closing also animates smoothly — a details pseudo-element nicety provided by the components file. Everywhere else the toggle is instant.

Printing note: the browser enforces one open panel per exclusive group, so printing "everything open" needs a beforeprint listener that removes the name attribute (and restores it after). The print stylesheet already forces the light palette, so dark-mode users get paper colors, not ink floods.

    Responsive composition

    mote's structural helpers already adapt to the available width; .mote-grid reflows its tracks and .mote-row wraps. Page composition still decides what deserves a full row on a phone. Use a deliberate page rule instead of scattering utility classes:

    • Card grids: let .mote-grid choose the track count. Tune --mote-grid-min; do not pin a column count.
    • Toolbars: .mote-row wraps, but controls keep their intrinsic widths. Stack them deliberately when each control needs the full width.
    • Header navigation: long pill rows scroll horizontally. Give the nav its own row on narrow screens when it needs more room, and keep primary actions outside the scrolling region.

    A narrow toolbar can be one page rule. Make .mote-row the toolbar owner so each label is a direct flex item:

    <div class="mote-row filter-bar">
  <label>Search
    <input type="search" name="q">
  </label>
  <label>Status
    <select name="status">
      <option>Active</option>
    </select>
  </label>
  <button type="button">Apply</button>
</div>

    This handles direct controls and controls wrapped in labels:

    @media (max-width: 30rem) {
  .filter-bar > :where(input, select, button),
  .filter-bar > label {
    flex: 1 1 100%;
  }

  .filter-bar > label :where(input, select) {
    width: 100%;
  }
}

    The first rule gives direct controls and labels a full row; the second makes a control inside a label fill that label. .mote-row wraps controls, but it does not make them full-width by itself. The page rule owns that choice; nested wrappers need their own selector.

    A sticky toolbar beneath a site header needs a matching offset. Use .mote-row for the toolbar's wrapping layout and .toolbar for its sticky placement; .toolbar is a page-owned class here, not a class mote ships:

    <div class="mote-row toolbar">
  <label>Search
    <input type="search" name="q">
  </label>
  <button type="button">Filter</button>
</div>

    The sticky top offset must match the header's actual bottom edge so the toolbar does not overlap it.     const pills = document.querySelector('header nav ul');
const sync = () => pills.parentElement.dataset.nav =
  (pills.scrollLeft > 1 ? 'start ' : '') +
  (pills.scrollLeft + pills.clientWidth < pills.scrollWidth - 1 ? 'end' : '');
pills.addEventListener('scroll', sync, { passive: true });
addEventListener('resize', sync);
sync();
document.fonts?.ready.then(sync);  // pill widths change when webfonts load

    Print and paper

    mote prints on a light paper palette in either theme. Use the print helpers when the screen and the page need different content, then add page CSS for the document-specific parts such as orientation and page breaks.

    Screen-only and paper-only content

    .mote-no-print removes screen chrome from paper. .mote-print-only stays hidden on screen and appears on paper:

    <nav class="mote-no-print">Site navigation</nav>
<div class="mote-print-only">Printed at the visitor’s request</div>

    Tables, disclosures, and page breaks

    With mote.components.css, .mote-table-scroll removes the screen height cap and clipping on paper. This guarantees that the complete table is present without artificial clipping; it does not guarantee that an arbitrary wide matrix fits narrow paper.

    The .mote-doc shell itself does not choose a paper layout. That remains page-owned: collapse the screen grid, remove the shell gutter, and let the main region show its complete content. Mark navigation and other screen chrome with .mote-no-print when it should not appear on paper:

    @media print {
  body.mote-doc {
    display: block;
    padding-inline: 0;
  }
  body.mote-doc > main {
    overflow: visible;
  }
}

    This is the boundary between mote's component behavior and the page's print design. The complete light palette and table expansion are shipped; the shell's paper arrangement is not.

    For a document or dedicated print output containing a dense matrix, landscape paper may be clearer than forcing many columns into portrait. This @page rule applies to the whole printed document:

    @page {
  size: landscape;
  margin: 12mm;
}

    For a document that mixes portrait and landscape sections, keep the landscape matrix in a separate print document rather than applying this rule to every page.

    Check the generated PDF. Reducing type and padding can fit more columns but may force words to break; when many columns cannot remain legible, use the semantic record layout from Narrow screens: scroll or transform instead of forcing the matrix onto the page.

    Chromium repeats a tfoot totals row at the top of each continuation page, where its colspan cells no longer line up with the columns. The data is complete; the repeated row is browser pagination. Keep the totals in tbody when the alignment matters.

    mote's sticky site header goes static on paper, so it does not repeat over every page. A print-specific layout may restore position: sticky, but repetition across pages depends on the browser's paged-media implementation and is not guaranteed. Inspect the generated PDF; use the print engine's page-header mechanism when every page must carry a running head.

    The phone-record layout keeps the table a table on paper: the recipe's print guard restores the hidden header row and the caption.

    Keep important tables intact with a small page rule:

    @media print {
  .receipt, tr, figure { break-inside: avoid; }
}

    A closed details element does not guarantee that its hidden content reaches paper. If a manual must print every disclosure, open them in a beforeprint handler and restore their previous state in afterprint. Exclusive groups also need their shared name removed while printing, or the browser allows only one panel open. This complete page-level handler selects every disclosure, including unnamed panels, and preserves the original state:

    const disclosures = [...document.querySelectorAll('details')];
let printState = [];

addEventListener('beforeprint', () => {
  if (printState.length === 0) {
    printState = disclosures.map(details => ({
      details,
      name: details.getAttribute('name'),
      open: details.open
    }));
  }
  for (const { details, name } of printState) {
    if (name !== null) details.removeAttribute('name');
    details.open = true;
  }
});

addEventListener('afterprint', () => {
  for (const { details, name, open } of printState) {
    if (name !== null) details.setAttribute('name', name);
    details.open = open;
  }
  printState = [];
});

    Print helpers live in the helper map, but this section keeps the complete disclosure workflow together.
