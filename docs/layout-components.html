Layout and components

Compose pages from landmarks and a small set of CSS-only helpers. The platform supplies the behavior; mote supplies the finish.

Layout

Layout pieces from mote.components.css — default modern CSS, no JavaScript, no column utilities, no breakpoints. The document shell below is the whole story: header, nav, aside and footer flex from plain landmarks, and the sticky translucent header on this very page is the same pattern. The semantic selectors (nav[aria-label]) match their values case-sensitively — copy the exact lowercase ("breadcrumb", "pagination", "toc").

Simple page

Most pages need nothing more than a sticky header and a centered column — the layout of the page you are reading, plus the contents rail beside it. The header bar and its pill nav style themselves from landmarks; the classes on the inner div are the layout: .mote-container adds the gutters, .mote-row flexes, .mote-brand quiets the wordmark, .mote-push right-aligns the last control:

<body>
  <header>
    <div class="mote-container mote-row">
      <a href="/" class="mote-brand">Brand</a>
      <nav>
        <ul>
          <li><a href="/">Home</a></li>
          <li><a href="/docs">Docs</a></li>
        </ul>
      </nav>
      <button type="button" class="mote-push">Toggle</button>
    </div>
  </header>
  <main class="mote-container">
    <h1>Page title</h1>
    <p>Content…</p>
  </main>
</body>

Scope matters: body > header is the site-shell selector. A header that is a direct child of body receives the sticky translucent treatment even when it also has .mote-container or other classes. Wrapping that header in a plain wrapper element is the intentional opt-out: the landmark selector cannot reach it, so it stays in ordinary flow. Keep a direct site header compact on phones because it remains in the viewport while the page scrolls.

Centering stays opt-in because full-bleed pages are equally valid. If your shell is wrapped in a framework-provided wrapper (some frameworks do), .mote-header and .mote-nav bring the same styles to headers the landmark selector cannot see.

For a narrower reading column (long-form articles), set --mote-container-max — 42rem is a comfortable measure:

<main class="mote-container" style="--mote-container-max: 42rem">

A footer after main follows normal flow — fine for long pages. If you want it pinned to the viewport bottom even when content is short, use the document shell below.

Right-align content in rows with .mote-push:

<div class="mote-row">
  <strong>Brand</strong>
  <nav>…</nav>
  <button class="mote-push">Toggle</button>
</div>

Responsive composition

mote's structural helpers already adapt to the available width; .mote-grid reflows its tracks and .mote-row wraps. Page composition still decides what deserves a full row on a phone. Use a deliberate page rule instead of scattering utility classes:

  • Card grids: let .mote-grid choose the track count. Tune --mote-grid-min; do not pin a column count.
  • Toolbars: .mote-row wraps, but controls keep their intrinsic widths. Stack them deliberately when each control needs the full width.
  • Header navigation: long pill rows scroll horizontally. Give the nav its own row on narrow screens when it needs more room, and keep primary actions outside the scrolling region.

A narrow toolbar can be one page rule. Make .mote-row the toolbar owner so each label is a direct flex item:

<div class="mote-row filter-bar">
  <label>Search
    <input type="search" name="q">
  </label>
  <label>Status
    <select name="status">
      <option>Active</option>
    </select>
  </label>
  <button type="button">Apply</button>
</div>

This handles direct controls and controls wrapped in labels:

@media (max-width: 30rem) {
  .filter-bar > :where(input, select, button),
  .filter-bar > label {
    flex: 1 1 100%;
  }

  .filter-bar > label :where(input, select) {
    width: 100%;
  }
}

The first rule gives direct controls and labels a full row; the second makes a control inside a label fill that label. .mote-row wraps controls, but it does not make them full-width by itself. The page rule owns that choice; nested wrappers need their own selector.

A sticky toolbar beneath a site header needs a matching offset. Use .mote-row for the toolbar's wrapping layout and .toolbar for its sticky placement; .toolbar is a page-owned class here, not a class mote ships:

<div class="mote-row toolbar">
  <label>Search
    <input type="search" name="q">
  </label>
  <button type="button">Filter</button>
</div>

The sticky top offset must match the header's actual bottom edge so the toolbar does not overlap it. Header height depends on its content — and on how many rows it takes at that width — so keep the value page-owned and measure it rather than estimating: scroll the page and read the header's bottom edge in the console

document.querySelector('header').getBoundingClientRect().bottom

Use that value for the layout you are in:

:root {
  --toolbar-top: 4.75rem;
}

.toolbar {
  position: sticky;
  top: var(--toolbar-top);
}

@media (max-width: 40rem) {
  :root {
    --toolbar-top: 7.5rem;
  }
}

Those numbers are examples for one header, not defaults: a one-row and a two-row header need two different offsets, and a two-row header can be taller than any fixed sample. Measure every width you ship.

The complete header recipe is in Header and navigation. For wide data, choose between an internal scroll region and a record layout in Narrow screens: scroll or transform.

Hero and bands

Two helpers for focused layouts:

.mote-hero centers content in the remaining viewport height — error pages, login screens, empty states. The offset clears a header and footer; tune it per page with --mote-hero-offset (default 12rem):

<main class="mote-container mote-hero">…</main>

<!-- taller header/footer: raise the offset -->
<main class="mote-container mote-hero" style="--mote-hero-offset: 14rem">…</main>

Hero scaled to fit this page via the offset — on a real error page the default 12rem gives the block nearly the full viewport.

.mote-band is a full-bleed tinted section — CTA bands, section dividers, announcement strips. The mix is opaque, so it reads as a deliberate section in both palettes (unlike --mote-accent-soft, which is transparent and can vanish over dark backgrounds). Bands are content surfaces: a status class on the band or an ancestor tints them. The band provides color and breathing room; the container inside provides the gutters. The band itself goes outside the container — a sibling of main — or it bleeds only to the container edge:

<section class="mote-band">
  <div class="mote-container">
    <h2>Ready when you are.</h2>
    <p><a class="mote-btn" href="/signup">Create account</a></p>
  </div>
</section>

Document layout

One class on <body> turns the landmarks you already write into the layout: header and footer span the page, a nav becomes a sticky left rail, an aside a right rail, and main takes the middle. Everything collapses to a single column under 50rem, keeping the landmarks in source order. No classes on the landmarks themselves:

On <body> the shell includes page gutters, a pinned footer and content tracks that absorb wide content (minmax(0, 1fr)). A wide table scrolls inside main, never the page; when a table needs a sticky header or a height cap, wrap it in .mote-table-scroll so that component owns the horizontal scroll instead. The body shell already has page gutters — avoid adding another .mote-container inside main unless that narrower measure is intentional. The nav rail is a quiet vertical list by default. When a sticky site header (body > header) exists, the rail top and the scroll padding for anchor jumps derive themselves — nothing to set. Set --mote-rail-top only for wrapped shells (.mote-header, which the landmark selector cannot see) or a custom offset:

:root {
  --mote-rail-top: 4.75rem;  /* wrapped shells only — landmarks do this for you */
}

<body class="mote-doc">
  <header>Site header</header>
  <nav>
    <ul>
      <li><a href="#">Docs</a></li>
      <li><a href="#">Blog</a></li>
    </ul>
  </nav>
  <main>
    <p>Your content.</p>
  </main>
  <aside>Contextual notes</aside>
  <footer>© mote</footer>
</body>

Header and navigation

Direct children of <body> get these styles from landmarks alone. A direct body > header is the sticky translucent site shell; keep it compact on phones because it remains in the viewport while the page scrolls. The classes exist for one case landmarks cannot express — a shell wrapped in a <div>, where body > header cannot reach it:

<header class="mote-header">
  <nav class="mote-nav">
    <ul>
      <li><a href="/" aria-current="page">Home</a></li>
      <li><a href="/docs">Docs</a></li>
    </ul>
  </nav>
</header>

Long navs scroll horizontally inside the bar — a section list of any length keeps the header one line, and the brand and pushed controls keep their place. Under the pills a hairline carries directional fades that bloom toward whichever side holds more content. Pure CSS cannot tell "at the start" from "nothing to scroll", so the fades key off a data-nav attribute kept current by the seven-line snippet below — without it there is no line at all: zero-JS headers keep just the pills, and the cut pill is the overflow signal. With the snippet, the hairline appears only while the nav actually scrolls: a single pill leaves nothing on the line — and on wide viewports, where the pills never overflow, there is nothing to see at all. The snippet's math is direction-agnostic; the gradients flip under [dir="rtl"]. Breadcrumbs need no class at all — mote styles the semantic pattern:

const pills = document.querySelector('header nav ul');
const sync = () => pills.parentElement.dataset.nav =
  (pills.scrollLeft > 1 ? 'start ' : '') +
  (pills.scrollLeft + pills.clientWidth < pills.scrollWidth - 1 ? 'end' : '');
pills.addEventListener('scroll', sync, { passive: true });
addEventListener('resize', sync);
sync();
document.fonts?.ready.then(sync);  // pill widths change when webfonts load

On narrow screens, the brand and pushed controls can leave the scrolling nav with very little room. For a long navigation, give the navigation its own row and keep primary actions outside the scrolling region. The one-row fallback suits short navigation; its cut pill is the overflow signal when JavaScript is not used.

This rule is page CSS — copy it into your own stylesheet. mote does not ship it. It gives the navigation its own line in the header; the default bar already contains a long nav, by scrolling its pill row inside the bar. The recipe below applies to mote's canonical header composition, where .mote-row owns the header row. A custom flex header has its own layout owner and needs equivalent page rules for its own structure.

<header class="mote-header">
  <div class="mote-container mote-row">
    <a class="mote-brand" href="/">Northline</a>
    <nav class="mote-nav" aria-label="Sections">
      <ul>
        <li><a href="/overview">Overview</a></li>
        <li><a href="/fixtures">Fixtures</a></li>
        <li><a href="/results">Results</a></li>
      </ul>
    </nav>
    <a class="mote-btn mote-push" href="/apply">Apply</a>
  </div>
</header>

<style>
@media (width < 40rem) {
  :where(body > header, .mote-header) .mote-row {
    row-gap: 0.5rem;
  }
  :where(body > header, .mote-header) :where(nav, .mote-nav) {
    flex: 1 1 100%;
    order: 2;
    min-inline-size: 100%;
  }
}
</style>

The brand and primary action remain on the first row; the navigation gets the second row and keeps its own horizontal scroll behavior. If every label must be visible without scrolling, shorten the navigation or move secondary links into the page body.

<nav aria-label="breadcrumb">
  <ol>
    <li><a href="/">Home</a></li>
    <li><a href="/docs">Docs</a></li>
    <li><span aria-current="page">Layout</span></li>
  </ol>
</nav>

Pagination

Same idea as breadcrumbs — a semantic label, no class. mote styles the link row and the aria-current pill. The current page works best as a <span> (you are already there — not a link), but if you use an <a>, mote keeps the pill state visible on hover:

<nav aria-label="pagination">
  <ul>
    <li><a href="#top">← Prev</a></li>
    <li><a href="#top" aria-current="page">1</a></li>
    <li><a href="#top">2</a></li>
    <li><a href="#top">3</a></li>
    <li><a href="#top">Next →</a></li>
  </ul>
</nav>

Table of contents

Right-rail asides and "On this page" navigation, styled semantically like breadcrumbs and pagination. Inside .mote-doc, put the TOC in the aside to make it the right rail:

<nav aria-label="toc">
  <ul>
    <li><a href="#get-started">Get started</a></li>
    <li><a href="#theming">Theming</a></li>
  </ul>
</nav>
  • Get started
  • Theming
  • Elements

On a narrow screen, a long contents list should become a compact index rather than a tall block before or after the document. For this recipe, put the TOC in an aside before main: the narrow-screen .mote-doc column layout preserves that relative order visually, while native focus order follows DOM order. On wide screens, the document shell explicitly places that aside in the right rail. Start the disclosure closed and use the small documented script below to open it only on wide screens:

<body class="mote-doc">
  <header>…</header>
  <aside>
    <nav aria-label="toc">
      <details>
        <summary>On this page</summary>
        <ul>…</ul>
      </details>
    </nav>
  </aside>
  <main>…</main>
  <footer>…</footer>
</body>

<script>
  const toc = document.querySelector('nav[aria-label="toc"] details');
  const narrow = matchMedia('(width < 50rem)');
  const syncToc = () => { toc.open = !narrow.matches; };
  narrow.addEventListener('change', syncToc);
  syncToc();
</script>

Without JavaScript the contents stay closed and remain available by activating the summary. If the TOC deliberately follows main, keep that source order on every width; the shell will not reorder it for you. Mark navigational chrome that should not print with .mote-no-print.

The recipe above uses the aside so the contents become the right rail. A left-rail contents list is a different arrangement: put a nav directly before main in the source — the shell keeps it as the left rail on wide screens and above the content on narrow ones — and keep the reference material in the aside.

Card grids

One class; columns are computed from the container — as many 16rem cards as fit. auto-fill made column-count utilities obsolete. It may leave empty grid tracks when there are fewer cards than the container can hold; use .mote-grid-sparse when those empty tracks should collapse:

For wider or narrower tracks, set --mote-grid-min: 22rem gives 3-wide pricing; 26rem gives 2-column content. The default 16rem minimum suits compact cards; prose-heavy cards often need 22–26rem so their text has a comfortable measure:

<div class="mote-grid" style="--mote-grid-min: 22rem">
  <!-- 3 columns on any container >= 66rem -->
</div>

<div class="mote-grid">
  <article class="mote-card">…</article>
  <article class="mote-card">…</article>
  <article class="mote-card">…</article>
</div>

Featured cards read --mote-status for their border — one class tints the edge:

<article class="mote-card mote-success">

  <p>The status class tints the border.</p>

Flush-top media (cover photos, thumbnails) — the one compositional card pattern that ships as a class: .mote-card-media pulls the media edge-to-edge and matches the card radius:

.mote-card and .mote-media don't merge — the card's column direction wins over the media row. Nest the media inside the card. The class sizes a direct img, video, or inline svg child. A direct SVG keeps its own viewBox aspect ratio; nested SVG icons keep their own dimensions. A non-image cover block needs its own aspect-ratio and padding.

<article class="mote-card">
  <div class="mote-card-media">
    <img src="cover.jpg" alt="">
  </div>
  <h3>Card title</h3>
</article>

<article class="mote-card">
  <div class="mote-card-media">
    <svg viewBox="0 0 160 100" role="img" aria-label="Cover artwork">
      <rect width="160" height="100" fill="currentColor" opacity=".15"></rect>
    </svg>
  </div>
  <h3>Card title</h3>
</article>

Cards are vertical flex containers. When cards in one row have different copy lengths, keep their actions aligned at the bottom with a page-owned class:

<article class="mote-card">
  <h3>Card title</h3>
  <p>Different amounts of copy…</p>
  <div class="card-actions mote-row">
    <a class="mote-btn" href="#">Open</a>
    <a href="#">Details</a>
  </div>
</article>

Your class name can be anything. .mote-row still owns the action row's display, gap, and wrapping; the page rule only supplies margin-block-start: auto:

.mote-card > .card-actions { margin-block-start: auto; }

Badges

Badges are content markers — they declare their own status, never inherit from context (same gating as buttons). A plain .mote-badge is always accent-tinted; a status class on the badge itself provides the tint:

<span class="mote-badge">accent</span>
<span class="mote-badge mote-success">success</span>
<span class="mote-badge mote-warning">warning</span>
<span class="mote-badge mote-error">error</span>
<span class="mote-badge mote-info">info</span>
<span class="mote-badge mote-muted">muted</span>

accent success warning error info muted

Badges use min(0.8em, 0.8rem): they shrink with smaller surrounding text but never enlarge with headings. Inside a table (0.95em) or a small metadata strip, the badge scales down with its context.

Media objects

Avatar or icon beside body — forum posts, comments, chat, author boxes. .mote-media flexes the row; the last child grows. Rows align to flex-start — long content never stretches the avatar row:

<div class="mote-media">
  <img class="mote-avatar" src="…" alt="">
  <div><p>Post body…</p></div>
</div>

An inline SVG icon can stand in for an avatar. It does not carry the avatar helper's image styling, so give it a stable square size and keep it from shrinking with one page rule:

.club-icon {
  inline-size: 2.5rem;
  block-size: 2.5rem;
  flex: none;
}

Toasts

A styled popover pinned to the corner. Showing it takes one line — the browser handles stacking, Esc, and light-dismiss:

Use popover="manual" for toasts — auto popovers light-dismiss on any body click, which surprises notification text — and show one at a time, since multiple toasts pin to the same corner:

A conventional form submission does not need a toast. Without JavaScript, let the form navigate normally and render role="status" feedback on the result page. With progressive enhancement, show the documented toast after a successful submission. A native popovertarget button fits an action-triggered popover, but it is not a general substitute for reporting a submitted form:

<div popover="manual" class="mote-toast" id="toast">
  Saved. Everything is fine.
</div>

<script>
  const t = document.querySelector('#toast');
  t.showPopover();
  setTimeout(() => t.hidePopover(), 3000);
</script>
